# Functional Requirements — Shop Demand Forecasting MVP

**Input:** approved PRD (`PRD.md`) · **Version:** 1.0
**Scope:** CSV template → upload → validation → missing-date confirmation →
product selection → horizon selection → forecast → evaluation → chart/table →
CSV export → reset.

Requirements are implementation-neutral unless the PRD already fixed a
constraint. Every acceptance criterion is objectively testable.

---

## FR-01 · Provide a CSV template — *Must*

| | |
|---|---|
| **User value** | The manager knows exactly what to export from their till or spreadsheet. |
| **Trigger** | The user selects **Download CSV template** on the landing page. |
| **Preconditions** | None. Available before any upload. |

**Normal flow:** the browser downloads `sales-template.csv` containing the headers
`date,product,units_sold` and a single example row.

**Validation / error:** none required — the file is generated by the app.

**Acceptance criteria**

- **Given** the landing page, **when** the user selects "Download template",
  **then** a CSV downloads whose first row is exactly `date,product,units_sold`.
- **Given** the downloaded template, **when** it is opened, **then** it contains
  exactly one data row and that row is clearly an example.

---

## FR-02 · Upload one CSV — *Must*

| | |
|---|---|
| **User value** | Gets history into the tool in one step. |
| **Trigger** | The user selects or drops a file on the upload control. |
| **Preconditions** | A tabular export exists. |

**Normal flow:** the app reads the file in memory, then shows filename, row count,
date range and product count.

**Validation / error:** files that are not `.csv`, or are larger than 20 MB, are
rejected *before* parsing with a message naming the limit and the actual value.
An unreadable file produces a message asking for a UTF-8 CSV with a header row.

**Acceptance criteria**

- **Given** a valid CSV no larger than 20 MB, **when** it is uploaded, **then**
  the app shows filename, row count, date range and product count.
- **Given** a file of 21 MB, **when** the user tries to upload it, **then** the
  file is rejected and generation is impossible.
- **Given** a `.xlsx` file, **when** it is uploaded, **then** the app states that
  only `.csv` is accepted.

---

## FR-03 · Validate the required schema — *Must*

| | |
|---|---|
| **User value** | A misspelled header is explained instead of silently breaking the forecast. |
| **Trigger** | Any successful file read. |
| **Preconditions** | FR-02 passed. |

**Normal flow:** headers are normalised for letter case and surrounding
whitespace, then the three logical fields are required.

**Validation / error:** a missing or misspelled column blocks generation and the
message names both the expected and the received columns. Extra columns are
ignored with a visible warning.

**Acceptance criteria**

- **Given** a file whose header is `date,product,quantity`, **when** validation
  runs, **then** generation is blocked and the message names `units_sold` as
  expected and `quantity` as received.
- **Given** a header written as ` Date ` and `PRODUCT`, **when** validation runs,
  **then** the file is accepted.
- **Given** a file with an extra `promo_flag` column, **when** validation runs,
  **then** a non-blocking warning names that column.

---

## FR-04 · Validate field values — *Must*

| | |
|---|---|
| **User value** | Bad rows are located by row number, not discovered after a wrong order. |
| **Trigger** | Schema validation passed. |
| **Preconditions** | FR-03 passed. |

**Normal flow:** dates are parsed strictly as ISO, products are trimmed, and
`units_sold` is parsed as a non-negative whole number.

**Validation / error:** invalid dates, blank products, negative quantities,
fractional quantities, non-numeric quantities and duplicate `date`+`product`
pairs each block generation. Each report gives a count and up to five spreadsheet
row numbers. Duplicates are never silently summed.

**Acceptance criteria**

- **Given** a row containing `03/04/2026`, **when** validation runs, **then**
  generation is blocked and the report includes that row's spreadsheet number.
- **Given** rows with `-4`, `2.5` and `many` in `units_sold`, **when** validation
  runs, **then** three separate problems are reported with their row numbers.
- **Given** two rows with the same date and product, **when** validation runs,
  **then** generation is blocked with a duplicate-row message.
- **Given** two rows with the same date but different products, **when**
  validation runs, **then** the file is accepted.
- **Given** any blocking problem, **when** it is shown, **then** the message
  includes the affected field and the next corrective action.

---

## FR-05 · Resolve missing dates — *Must*

| | |
|---|---|
| **User value** | Prevents a silent, wrong assumption about gaps in the history. |
| **Trigger** | Validation passed and the selected product's series has calendar gaps. |
| **Preconditions** | FR-04 passed. |

**Normal flow:** the app states how many days are missing, shows up to five of
them, and asks whether a gap means zero sales.

**Validation / error:** until the user confirms, no forecast can be generated.
Choosing "do not forecast yet" keeps the run blocked and asks for corrected data.

**Acceptance criteria**

- **Given** a product with three missing calendar days, **when** validation
  finishes, **then** the app asks how to treat them and no generate control is
  offered.
- **Given** the same product, **when** the user confirms "treat missing days as
  zero sales", **then** the daily series is zero-filled and a forecast can run.
- **Given** the same product, **when** the user chooses "do not forecast yet",
  **then** no forecast can be produced.

## FR-06 · Select an eligible product — *Must*

| | |
|---|---|
| **User value** | Cannot pick a product whose history is too short to trust. |
| **Trigger** | The user opens the product list. |
| **Preconditions** | Valid data loaded. |

**Normal flow:** products are sorted alphabetically and each option shows its
available history length.

**Validation / error:** products with fewer than 90 observed days cannot be
selected; they are listed separately with the reason. If no product is eligible,
the selector is disabled and the minimum is restated.

**Acceptance criteria**

- **Given** valid data with products *Apple Pie*, *Mango Tart* and *zucchini loaf*,
  **when** the list opens, **then** the order is alphabetical and each entry shows
  its day count.
- **Given** a product with 45 days of history, **when** the list opens, **then**
  it is unavailable and the reason states that 90 days are required.
- **Given** every product has fewer than 90 days, **when** the list opens,
  **then** the selector is disabled with a visible explanation.

---

## FR-07 · Choose a horizon — *Must*

| | |
|---|---|
| **User value** | Matches the forecast length to the ordering cycle. |
| **Trigger** | An eligible product is selected. |
| **Preconditions** | FR-06 satisfied. |

**Normal flow:** the user selects 7 or 30 days; the choice drives the chart, the
table and the export.

**Validation / error:** changing the horizon invalidates any previous run so a
stale result cannot be exported.

**Acceptance criteria**

- **Given** an eligible product, **when** 30 days is selected, **then** the chart,
  table and exported CSV all contain exactly 30 forecast rows.
- **Given** a completed 7-day run, **when** the horizon changes to 30, **then**
  the previous run and its export control disappear.

---

## FR-08 · Generate forecast — *Must*

| | |
|---|---|
| **User value** | One click produces the daily numbers to order against. |
| **Trigger** | The user selects **Generate forecast**. |
| **Preconditions** | FR-05 through FR-07 satisfied. |

**Normal flow:** a loading state appears, then one prediction plus lower and upper
bounds is returned for every future date.

**Validation / error:** if the model cannot be trained, the seasonal baseline is
used and a warning explains the substitution. A failure never surfaces a stack
trace.

**Acceptance criteria**

- **Given** valid inputs, **when** Generate forecast is selected, **then** a
  loading indicator appears before results.
- **Given** a completed run, **then** each future date has one predicted value
  and, when available, a lower and an upper bound.
- **Given** any run, **then** every displayed prediction is a whole number and is
  zero or greater.

---

## FR-09 · Evaluate on holdout data — *Should*

| | |
|---|---|
| **User value** | Knows whether to trust the model or a simple rule of thumb. |
| **Trigger** | A run starts with at least 120 complete days of history. |
| **Preconditions** | A selected product with sufficient history. |

**Normal flow:** the most recent 28 days are withheld, MAE and WAPE are reported
for both the model and the seasonal-naive baseline, and the app states which
performed better.

**Validation / error:** below 120 days the section explains that evaluation is
unavailable and why. The baseline comparison is always shown, including when the
model wins. When actual units total zero, WAPE is reported as unavailable rather
than as a division error.

**Acceptance criteria**

- **Given** 200 days of history, **when** a forecast runs, **then** MAE and WAPE
  appear for both the model and the baseline, and the better performer is named.
- **Given** 100 days of history, **when** a forecast runs, **then** a reason is
  shown in place of the metrics.
- **Given** a run where the model wins, **then** the baseline score is still
  displayed.

---

## FR-10 · Display results — *Must*

| | |
|---|---|
| **User value** | Everything needed to decide, in one scroll. |
| **Trigger** | A run completes. |
| **Preconditions** | FR-08 succeeded. |

**Normal flow:** the page shows recent actuals, the forecast, the uncertainty
band, a daily table, the total predicted units, the evaluation, the run settings
and a limitations note.

**Validation / error:** status is never communicated by colour alone; every state
carries words plus an icon or heading. Chart values are repeated in the table.

**Acceptance criteria**

- **Given** a completed run, **then** the page shows a chart with actuals, a
  dashed forecast line and, when available, a shaded band.
- **Given** a completed run, **then** the daily table lists one row per forecast
  day and the chart's forecast values match it exactly.
- **Given** a completed run, **then** a visible limitations note appears before
  the download control.
- **Given** any status message, **then** its meaning is readable without relying
  on colour.

---

## FR-11 · Export results — *Must*

| | |
|---|---|
| **User value** | Takes the numbers into their ordering spreadsheet. |
| **Trigger** | The user selects **Download forecast CSV**. |
| **Preconditions** | A completed, current run exists. |

**Normal flow:** a CSV downloads containing `product`, `forecast_date`,
`predicted_units`, `lower_bound`, `upper_bound`, `horizon`, `model_version` and
`generated_at`.

**Validation / error:** the control is only rendered for a current run, so a
partial or stale result can never be exported. When bounds are unavailable the
columns are present but blank.

**Acceptance criteria**

- **Given** a completed run, **when** the CSV is downloaded, **then** it has
  exactly the eight required columns in that order.
- **Given** a completed run, **then** every `predicted_units` value equals the
  corresponding value in the on-screen table.
- **Given** a run with no uncertainty bounds, **then** the bound columns exist and
  are empty.

---

## FR-12 · Reset session — *Must*

| | |
|---|---|
| **User value** | Leaves no data behind on a shared shop computer. |
| **Trigger** | The user selects **Start over** and confirms. |
| **Preconditions** | None. Available in every state. |

**Normal flow:** the app asks for confirmation, then clears the uploaded file,
selections, cached model and results.

**Validation / error:** cancelling keeps the current session intact.

**Acceptance criteria**

- **Given** any state, **when** Start over is selected, **then** confirmation is
  requested before anything is cleared.
- **Given** the confirmation, **when** the user confirms, **then** the file,
  product, horizon, evaluation and results are all cleared and the export control
  disappears.
- **Given** the confirmation, **when** the user cancels, **then** the previous
  results remain.

## Cross-cutting: states and accessibility

| Area | Requirement |
|---|---|
| States | Loading, success, warning, empty and error each state the next action. |
| Keyboard | Every control is reachable and operable by keyboard, with a visible focus ring. |
| Labels | Every input has a programmatic and visible label. |
| Contrast | Body text meets WCAG AA against its background. |
| Non-colour cues | Status uses text and an icon or heading; chart series differ by line style and legend text, not colour alone. |
| Chart alternative | Every charted value is available in a table. |
| Disabled controls | A disabled control always has a visible nearby reason. |
| Privacy | Uploaded data is never written to logs; log lines contain counts, timings and status only. |
